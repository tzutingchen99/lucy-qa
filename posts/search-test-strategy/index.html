搜尋功能的測試策略

測試策略 系列 2 / 2

  • 1.一個登入功能，你會怎麼測
  • 2.搜尋功能的測試策略

TL;DR

搜尋看起來簡單，但邊界條件豐富、「正確」的定義往往模糊。開測之前先釐清搜尋範圍、排序依據、模糊搜尋支不支援；核心測試涵蓋有結果、沒結果、邊界輸入三種情況。重點不是把所有關鍵字都試一遍，是確認邊界行為（空搜尋、特殊字元）、安全性（XSS）、以及 empty state——這三塊最常出問題，也最容易被跳過。

搜尋比你想的複雜

搜尋功能看起來簡單：輸入關鍵字，看結果。

但搜尋涉及的技術層面多、邊界條件豐富、而且「正確」的定義往往很模糊。這讓它成為一個值得認真想策略的測試對象。

先釐清這個搜尋「應該做什麼」

搜尋功能的 spec 很少是完整的。在開始測之前，先確認：

  • 搜尋的範圍是什麼？（商品名稱？描述？tag？全文？）
  • 結果排序的依據是什麼？（相關性？時間？熱門度？）
  • 支援模糊搜尋嗎？（「iphon」要找到「iPhone」嗎）
  • 大小寫敏感嗎？
  • 空白鍵怎麼處理？（「iphone 14」和「iphone14」是同一個查詢嗎）

核心功能測試

有結果的情況：

  • 完整關鍵字
  • 部分關鍵字（如果支援模糊搜尋）
  • 大寫 / 小寫 / 混合

沒有結果的情況：

  • 確認 empty state 顯示正確
  • 確認有無建議（「是否要搜尋 X？」）

邊界輸入：

  • 空白搜尋（應該做什麼？全部顯示還是阻止）
  • 只有空格
  • 超長字串
  • 特殊字元：<script>、%、*、SQL 關鍵字

哪些不值得花太多時間

  • 每種可能的關鍵字組合：這是功能驗證，不是 QA 的事，更依賴搜尋引擎本身的品質
  • 搜尋速度：這是效能測試的範疇，手動測不出什麼意義
  • 所有特殊字元的排列組合：挑幾個代表性的就夠了

容易漏掉的地方

XSS：在搜尋欄輸入 <script>alert(1)</script>，確認不會被執行

搜尋記錄：如果有搜尋歷史功能，確認隱私行為（登出後清除？）

URL 參數：搜尋結果是否有對應 URL？URL 直接貼給別人能正確顯示嗎？

Loading state：搜尋過程中 UI 是否有 loading 指示？連線慢的情況下行為正確嗎？

一個結論

搜尋測試的重點不是把所有關鍵字都試一遍，是確認邊界行為（空搜尋、特殊字元）、安全性（XSS）、以及 empty state 是否正確——這三塊最常出問題，也最容易被跳過。
