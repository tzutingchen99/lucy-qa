Bug 重開了，是誰的問題

TL;DR

Bug 重開最容易變成「你修不好」vs「你沒驗到」的互相指責，但重開的原因——治標不治本、regression、驗收條件不清、環境差異——大多指向流程，不是某個人。比追責更有用的是找出這次重開的根因，把它帶進 retrospective，變成流程改善的素材

一個常見的緊張時刻

Bug 被標記為 Fixed，QA 驗收，關掉。隔幾天，同樣的問題又出現了

Bug 被重開了

這個時刻很容易變成指責的開始：「你修的不完整」vs「你驗收的時候怎麼沒發現」。但這兩個指責通常都只對了一半

Bug 重開的原因，大多是流程問題

原因一：修復沒有根治，只治了症狀

RD 修了表面的問題，但根本原因沒有被找到。這次修好了，下次換個條件又出現

原因二：修復影響了其他地方

這次的修復引入了 regression。QA 驗收了原本的 bug，但沒有測到受影響的其他功能

原因三：驗收條件不夠清楚

QA 和 RD 對「這個 bug 算修好了」的定義不一樣。QA 按照原本的步驟驗通過了，但 RD 修的其實是另一個層面的問題

原因四：環境差異

在測試環境驗通了，但 production 的資料狀態或配置不同，問題在 production 上重現

誰的問題

直接說：通常是流程的問題，不是某一個人的問題

  • 如果是根本原因沒找到：這是 RD 需要更深入分析的問題，但 QA 在回報時有沒有提供足夠的資訊來幫助根因分析？
  • 如果是 regression：QA 的 regression 測試範圍夠嗎？還是 RD 改了一個地方但沒告知影響範圍？
  • 如果是驗收條件不清楚：這是需求和溝通的問題，不是任何一方的錯

比追責更有用的事

Bug 重開了，比追責更值得做的是：

  1. 搞清楚這次重開的根因
  2. 這個根因是流程上的什麼問題
  3. 下次要怎麼避免同樣的事發生

把這個討論帶到 retrospective，讓它成為改善流程的素材，而不是停留在「你搞的」這個層次

一個結論

Bug 重開不是誰的問題，是一個訊號：某個環節的流程沒有到位。追責不解決問題，找根因才能防止下次發生
