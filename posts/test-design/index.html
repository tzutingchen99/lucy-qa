靠感覺測試的問題不是「測太少」，是「不知道少了什麼」。等價分割決定測哪幾區、邊界值盯最容易出事的點、決策表把組合列全、狀態轉換抓非法路徑——把「感覺要測」變成「知道為什麼測」

測試靠感覺的問題

你在測一個年齡輸入欄位，接受 18 到 65 歲。你寫了三個測試案例：輸入 25、輸入 0、輸入 100

感覺夠了。但 17 跟 18 的行為不同嗎？65 跟 66 呢？負數會怎樣？小數點會怎樣？

靠感覺測試的問題不是「測太少」，是「你不知道少了什麼」。下面這幾個方法不是公式，是幫你把「感覺要測這個」變成「我知道為什麼要測這個」的框架

Test Case vs Test Scenario

先把這兩個詞分清楚，因為有時候會發現大家說的是不同的東西

Test Scenario（測試情境）：一條使用者旅程，描述「做什麼」 例如：「使用者用錯誤密碼登入三次後帳號被鎖定」

Test Case（測試案例）：具體的一筆驗證，有輸入、步驟、預期結果 例如：

前置條件：帳號存在，尚未被鎖
步驟：輸入正確帳號 + 錯誤密碼，重複三次
預期：第三次失敗後顯示「帳號已鎖定」，無法再嘗試登入

一個 Scenario 可以拆出多個 Test Case。Scenario 讓你看「這條路值不值得測」，Test Case 讓你知道「怎麼測、怎麼判斷有沒有過」

Equivalence Partitioning（等價分割）

核心邏輯：同一類輸入，行為應該一樣，測一個代表值就夠了

以年齡輸入（18–65）為例：

分區 範圍 代表值
有效區間 18–65 30
太小 < 18 10
太大 > 65 80

不需要測 10、11、12、13⋯⋯因為理論上這些輸入行為一樣，全部都應該被拒絕。測一個代表值就代表了整個分區

這個方法省力的地方在於：把無限可能的輸入，收成幾個有意義的類別

Boundary Value Analysis（邊界值分析）

等價分割告訴你哪幾區，邊界值分析說的是邊界是最容易出問題的地方，值得多測幾個點

>= 18 被寫成 > 18，<= 65 被寫成 < 65——差一個字元，行為完全不同。這種錯誤很常見

每個邊界測三個值：邊界本身、邊界內一個、邊界外一個

以 18–65 為例：

17（邊界外，應拒絕）
18（邊界，應通過）
19（邊界內，應通過）

64（邊界內，應通過）
65（邊界，應通過）
66（邊界外，應拒絕）

搭配等價分割一起用：分割決定「測哪幾區」，邊界值決定「每區的邊緣要多留意」

Decision Table（決策表）

有多個條件組合的時候，靠感覺很容易漏掉某個組合

假設折扣規則：

  • 會員 + 訂單 > 1000 → 打八折
  • 會員 + 訂單 ≤ 1000 → 打九折
  • 非會員 + 訂單 > 1000 → 打九五折
  • 非會員 + 訂單 ≤ 1000 → 不打折
會員 訂單 > 1000 預期折扣
是 是 八折
是 否 九折
否 是 九五折
否 否 不打折

把所有組合列出來，就知道要寫幾個 test case、有沒有漏掉

State Transition（狀態轉換）

有明確流程和狀態的功能適合用這個：訂單、帳號、審核流程

核心問題：每個狀態可以接受哪些事件？不應該發生什麼？

以訂單狀態為例：

待付款 --[付款成功]--> 已付款
已付款 --[出貨]--> 配送中
配送中 --[簽收]--> 已完成
待付款 --[取消]--> 已取消

正常路徑容易想到，但非法轉換才是 bug 常藏的地方：已完成的訂單能不能被取消？已取消的訂單能不能付款？這些邊角的場景很容易被跳過

一個結論

這些方法不是公式，是幫你把「感覺上應該測這個」轉成「我知道為什麼測這個」。有了依據，漏掉的東西就比較少
