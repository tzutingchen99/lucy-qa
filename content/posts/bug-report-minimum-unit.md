# Bug Report 的最小單位是什麼

## 為什麼很多 bug report 沒辦法被用

收到一個 bug report 說「這個壞掉了」——然後呢？

RD 不知道怎麼重現，QA 不知道要驗什麼，PM 不知道這是不是他說的那個問題。這個 bug 在系統裡掛著，沒人動，因為沒人知道從哪裡開始。

問題不是懶，是那個 bug report 本來就缺了一個東西：**可以被重現的步驟**。

---

## 可重現，是第一條

一個 bug report 最小要包含的東西，只有一個：讓別人能重現這個問題的足夠資訊。

不是描述症狀，是給重現路徑。

**症狀**：「購物車沒辦法結帳」

**重現路徑**：
1. 登入帳號 A（測試帳號資訊附上）
2. 加入商品 X 到購物車
3. 點擊結帳
4. 在付款方式選「信用卡」
5. 點擊「確認付款」
6. 出現 500 錯誤，訂單未建立

這兩個描述說的是同一件事，但只有第二個讓 RD 可以直接動手。

---

## 「最小」不代表「最少字」

最小單位不是字數最少，是讓問題能被重現的**最小資訊集合**。

有時候這需要很多字，因為重現條件很特定：
- 特定帳號、特定權限
- 特定瀏覽器版本
- 特定時間點（例如跨日的邊界）
- 特定資料狀態（例如購物車裡有某種組合的商品）

把這些都寫進去，不是囉嗦，是讓 bug 可以被解決的必要條件。

---

## 預期行為，是容易被忘的那個

除了重現步驟，還有一個常被省略的欄位：**預期結果是什麼**。

有些 bug 看起來「很明顯」，所以沒人覺得需要寫預期。但「明顯」是主觀的——QA 覺得明顯，RD 不一定，PM 更不一定。

特別是當「壞掉的行為」跟「舊有行為」有點像的時候，預期結果說清楚，就是讓三方不用再開一次會對齊的方式。

---

## 一個結論

> **Bug report 的最小單位不是一句話，是一條可重現的路徑 + 預期結果。少了這兩個，它不是 bug report，是問題描述。**
